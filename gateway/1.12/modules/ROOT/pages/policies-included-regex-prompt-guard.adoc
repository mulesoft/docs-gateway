== Summary

NOTE: This policy supports OpenAI and Anthropic input formats.

The Regex Prompt Guard policy scans LLM prompts and blocks requests when prompt content matches regex deny-list patterns.

The policy uses the Rust https://crates.io/crates/regex[regex crate] which supports RE2-style expressions to guarantee linear-time matching and eliminate the backtracking risk.

For example, you can use the policy to block attacks such as:

* Prompt injection
* Jailbreak attempts
* SQL injection patterns
* HTML script injection

== Response on Block

When a request is blocked, the policy returns a response body containing the matched deny patterns:

[source,json]
----
{
  "error": "Request blocked - content matches denied pattern",
  "matched_patterns": [
    "prompt-injection"
  ]
}
----

== Regex Support

The Regex Prompt Guard Policy uses the Rust https://crates.io/crates/regex[regex crate] which supports RE2-style expressions to guarantee linear-time matching and eliminate the backtracking risk. This ensures that customer-supplied regex patterns can't negatively impact gateway performance or availability.

The Regex Prompt Guard policy doesn't support Perl Compatible Regular Expressions (PCRE) because PCRE patterns can cause catastrophic backtracking that results in performance degradation or denial of service.

The policy does support these PCRE features:

* Standard character classes
* Alternation
* Grouping
* Greedy or lazy quantifiers
* Anchors
* Inline flags, such as `(?i)`, for case-insensitivity.

These PCRE-specific features aren't supported:

* Lookaround assertions: `(?=...)`, `(?!...)`, `(?<=...)`, `(?<!...)`
* Backreferences: `\1`, `\2`, `(?P=name)`
* Recursive or subroutine calls: `(?R)`, `(?1)`
* Possessive quantifiers: `a*+`, `a++`
* Special constructs: `\G`, `\K`, and conditional patterns `(?(1)yes|no)`
