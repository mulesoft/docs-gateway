[[summary]]
== Summary

The OAuth 2.0 Token Broker Connect (Authorization Code) policy is the inbound half of the OAuth 2.0 Token Broker. It works together with the xref:policies-outbound-oauth-token-broker.adoc[Credential Injection OAuth 2.0 Token Broker (Authorization Code) policy], which adds each user's own upstream token to outbound requests.

You apply this policy to two kinds of API instances, one per role:

* *`Endpoints` role: a single dedicated API instance* (for example, with the base path `/oauth2`) that hosts the connect flow. When a user hasn't connected an upstream account yet, they open a link. The policy asks them to sign in with your company identity provider, so Omni Gateway knows the person opening the link is the person who made the request. It then sends them to the upstream service to approve access, and stores the resulting connection securely.
* *`Framing` role: each MCP server API instance* that clients call. It presents the "authorization required" response in the format the client understands best. It needs no secrets.

When a user hasn't connected an upstream account yet:

* MCP clients that support URL prompts receive a prompt that opens the connect page.
* Other MCP clients receive a tool result that contains the link and the text from the authorization message. After the user approves access, they retry the request.
* Other clients receive a `403` response with a JSON body containing `authorization_url` and `authorization_id`, and an `x-flex-authorization-url` header.

[[before-you-begin]]
== Before You Begin

* Create the dedicated API instance that hosts the connect flow (for example, with the base path `/oauth2`) and decide its public address.
* Register Omni Gateway as a client at each upstream authorization server, with this redirect URI: `\{endpointsUrl}/callback`.
* Register Omni Gateway as a client at your company identity provider, with this redirect URI: `\{endpointsUrl}/login-callback`.
* Apply a token validation policy, such as JWT Validation or Token Introspection, to each MCP server API instance so the user is identified.
* Apply the Credential Injection OAuth 2.0 Token Broker (Authorization Code) policy to each upstream service.
* If you run more than one Omni Gateway replica, configure shared storage (Redis) so all replicas see the same connections. Connections, authorization state, and client secrets are encrypted at rest.

[[recommended-policy-chain]]
== Recommended Policy Chain

Apply these policies in this order on each MCP server API instance:

. xref:policies-included-oauth-token-broker-connect.adoc[OAuth 2.0 Token Broker Connect (Authorization Code)], with the role set to `Framing`.
. Token validation, such as xref:policies-included-jwt-validation.adoc[JWT Validation] or xref:policies-included-oauth-token-introspection.adoc[Token Introspection], to identify the caller.
. xref:policies-included-header-removal.adoc[Header Removal], with *Inbound Header Map* set to `authorization`.
. xref:policies-included-mcp-support.adoc[MCP Support].
. xref:policies-included-mcp-schema-validation.adoc[MCP Schema Validation], strongly recommended. See <<use-mcp-schema-validation>>.
. xref:policies-outbound-oauth-token-broker.adoc[Credential Injection OAuth 2.0 Token Broker (Authorization Code)], on the upstream service.

The dedicated API instance that hosts the connect flow needs only the Connect policy with the `Endpoints` role.

[[use-mcp-schema-validation]]
=== Use MCP Schema Validation

Set *Validate Tool Schema* to `true` and select the MCP server's Exchange asset. Omni Gateway then answers `tools/list`, `resources/list`, and `prompts/list` from the asset without requiring the user to connect first. Users see the real tools before they authorize.

The first denied request is usually a `tools/call`. Clients that support URL prompts, such as Claude Code and MCP Inspector, receive a native `-32042` response and prompt the user to connect.

Without MCP Schema Validation, Omni Gateway falls back to a synthetic `get_authorization_link` tool, empty lists, and a mocked `initialize` response until the user authorizes. Clients that don't support URL prompts show a connection error on the first attempt.

[[prevent-token-passthrough]]
=== Prevent Token Passthrough

The user's single sign-on (SSO) token must never reach the upstream service. Header Removal makes the Credential Injection policy the only source of the upstream `Authorization` header. If your clients send the token in another header, add that header to *Inbound Header Map* in the Header Removal policy.

[[how-this-policy-works]]
== How This Policy Works

This diagram shows how the pieces fit together. An MCP client calls an MCP server API instance that has the `Framing` role. The user's browser calls the dedicated API instance that has the `Endpoints` role. Both instances connect to the upstream service and your identity provider.

.Connect flow
----
MCP client ──► MCP server API instance (Connect: Framing)
                    │  Credential Injection policy on the upstream service
                    ▼
             Upstream service (for example, GitHub)

User's browser ──► Dedicated API instance, for example /oauth2 (Connect: Endpoints)
                    ├─ /authorize       starts the flow
                    ├─ /login-callback  returns from your identity provider
                    └─ /callback        returns from the upstream authorization server
----

. A client calls an MCP server API instance. Your authentication policy identifies the user, and the Credential Injection policy looks for that user's connection to the upstream service.
. If there's no connection, the request isn't forwarded. The `Framing` instance answers with a link to the `/authorize` page of the dedicated instance.
. The user opens the link, signs in with your identity provider, and approves access at the upstream service.
. Omni Gateway stores the connection. The user retries the request, and it succeeds.

[[browser-sign-in]]
=== Browser Sign-In

The user who signs in at the identity provider must be the same user who made the original request. Otherwise, Omni Gateway rejects the callback with a `403` response.

[[addresses]]
=== Addresses

Omni Gateway builds these addresses from the *Endpoints URL*. These examples use `\https://gateway.example/oauth2`:

[%header%autowidth.spread,cols="a,a,a"]
|===
| Purpose | Address | Example

| Link users open
| `\{endpointsUrl}/authorize`
| `\https://gateway.example/oauth2/authorize`

| Return from the upstream service
| `\{endpointsUrl}/callback`
| `\https://gateway.example/oauth2/callback`

| Return from your company identity provider
| `\{endpointsUrl}/login-callback`
| `\https://gateway.example/oauth2/login-callback`
|===

Register the last two addresses exactly as shown at the upstream authorization server and at your company identity provider. If the address that users' browsers reach differs from the *Endpoints URL*, sign-in fails when the browser returns to Omni Gateway.

[[limitations]]
=== Limitations

* Browsers keep the sign-in cookies only over HTTPS (or `localhost`), so use an `https` address for the *Endpoints URL*. The policy logs a warning when the address is plain `http` to another host.
* A proxy or load balancer in front of Omni Gateway must keep the path unchanged: the path in the *Endpoints URL* is both matched and published. Changing only the host, port, or scheme doesn't affect the policy.
* Federation isn't supported in this release. Federation is a single instance that aggregates several upstream servers, and it's the use case for the `Both` role. Federation with per-user brokered upstreams fails.
* The policy defaults to the `Both` role, so always set the role explicitly to `Endpoints` or `Framing`.
* This policy isn't supported with On-Behalf-Of upstreams.
* When the upstream rejects a user's token, clients receive a standard HTTP response (`503` or `403`) instead of an MCP message. Some MCP clients show this as a connection error on the first attempt and show the connect link only when they retry.
* Connections are tied to the identity Omni Gateway sees. If users sign in with different identities in different places, make sure the identity settings produce the same values.
