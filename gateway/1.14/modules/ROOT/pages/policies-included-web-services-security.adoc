== Summary

NOTE: The Web Services Security policy supports only WSDL (SOAP 1.1 and 1.2) APIs.

The Web Services Security policy protects a SOAP service by validating the `<wsse:Security>` header of each inbound request. You can enable either or both of these controls:

* *UsernameToken validation*: Authenticates the `<wsse:UsernameToken>` against the client applications that have contracts with the API. The username is the client ID, and the password is the client secret.
* *XML signature validation*: Verifies the `<ds:Signature>` in the Security header and confirms that the signing X.509 certificate chains to a certificate authority (CA) that you trust.

When you enable both controls, the request must carry a trusted signature that covers the UsernameToken, and the UsernameToken must match an API contract.

The policy is fail-closed. Every enabled control must succeed before Omni Gateway forwards the request to the upstream service. Omni Gateway forwards the original headers and body unchanged, and doesn't modify responses. When a check fails, Omni Gateway returns a Web Services Security SOAP fault, and the request never reaches the upstream service.

The policy accepts plain SOAP requests with a `text/xml` or `application/soap+xml` content type, and multipart SOAP requests with a `multipart/related` content type, such as MTOM/XOP and SOAP with Attachments (SwA).

* To validate UsernameTokens, client applications must have a contract with the API. For more information, see xref:api-manager::manage-client-apps-latest-task.adoc[].
* To validate XML signatures, get the PEM-encoded certificates of the CAs that issue your client signing certificates.

=== Configuration Examples

Examples that enable `validateUsernameToken` are only valid for Mnaged Gateway or Connected Mode.

This example enables both controls:

[source,yaml]
----
- policyRef:
    name: ws-security-policy-flex
  config:
    validateUsernameToken: true
    validateSignature: true
    trustAnchors: |
      -----BEGIN CERTIFICATE-----
      MIID...issuing-or-root-CA...
      -----END CERTIFICATE-----
----

This example enables only UsernameToken validation. The policy doesn't require, inspect, or trust an XML signature:

[source,yaml]
----
- policyRef:
    name: ws-security-policy-flex
  config:
    validateUsernameToken: true
    validateSignature: false
----

This example enables only XML Signature validation. The signature must cover the Timestamp. The policy doesn't require or authenticate a UsernameToken:

[source,yaml]
----
- policyRef:
    name: ws-security-policy-flex
  config:
    validateUsernameToken: false
    validateSignature: true
    trustAnchors: |
      -----BEGIN CERTIFICATE-----
      MIID...issuing-or-root-CA...
      -----END CERTIFICATE-----
----

== How This Policy Works

The policy validates each request in the following order. If a step fails, Omni Gateway stops processing the request and returns the fault for that step. Steps 5 through 7 run only when *Validate XML Signature* is enabled, and step 8 runs only when *Validate UsernameToken* is enabled.

. Omni Gateway confirms that the request's content type is `text/xml`, `application/soap+xml`, or `multipart/related`. For a `multipart/related` request, Omni Gateway also confirms that the multipart body is well-formed and selects the root part that contains the SOAP envelope.
. Omni Gateway confirms that the SOAP envelope is a single, well-formed SOAP 1.1 or SOAP 1.2 document.
. Omni Gateway confirms that the SOAP `<Header>` contains exactly one `<wsse:Security>` element as a direct child.
. Omni Gateway confirms that the Security header contains exactly one of each element that the enabled validations require, such as the `<wsse:UsernameToken>` or the `<ds:Signature>`. Omni Gateway rejects the request if the Security header contains XML Encryption elements.
. Omni Gateway confirms that the signature uses the supported algorithms: Exclusive XML Canonicalization, RSA-SHA256, and SHA-256 reference digests. The signature's `<ds:KeyInfo>` must reference an X.509 `<wsse:BinarySecurityToken>` in the same Security header.
. Omni Gateway confirms that the signing certificate chains to a certificate in *Trust Anchors (PEM)*, through no more than eight issuer certificates.
. Omni Gateway verifies the signature and the digest of every signed reference. The signed references must include the `<wsu:Timestamp>`. When *Validate UsernameToken* is also enabled, the signed references must also include the `<wsse:UsernameToken>`.
. Omni Gateway authenticates the UsernameToken by using the username as the client ID and the `PasswordText` password as the client secret. The credentials must match an API contract.

=== UsernameToken Validation

When UsernameToken validation is enabled, the Security header must contain exactly one `<wsse:UsernameToken>` with a username and a password:

* The password must be `PasswordText`. When the `<wsse:Password>` element has no `Type` attribute, the policy treats the password as `PasswordText`.
* The policy always rejects `PasswordDigest` because it can't access the client secret in clear text to recompute the digest.
* Omni Gateway applies Unicode NFC normalization to the username before it looks up the client ID.

If API contracts aren't available, for example, while Omni Gateway waits for the first contract update from Anypoint Platform, Omni Gateway returns a server fault. The request can succeed after the contracts load.

=== XML Signature Validation

When XML Signature validation is enabled, the Security header must contain:

* Exactly one `<wsu:Timestamp>`.
* Exactly one `<ds:Signature>`.
* A `<wsse:BinarySecurityToken>` that contains the signing certificate.

The signature must cover the Timestamp. When UsernameToken validation is also enabled, the signature must also cover the UsernameToken. The policy doesn't require the SOAP Body to be signed, but it verifies any Body reference that the signature includes.

==== Supported Algorithms

The policy supports only these algorithms. It rejects a signature that uses any other algorithm:

[%header%autowidth.spread,cols="a,a"]
|===
| Purpose | Algorithm

| Signature
| RSA-SHA256 (`\http://www.w3.org/2001/04/xmldsig-more#rsa-sha256`)

| Canonicalization
| Exclusive XML Canonicalization without comments (`\http://www.w3.org/2001/10/xml-exc-c14n#`)

| Reference digest
| SHA-256 (`\http://www.w3.org/2001/04/xmlenc#sha256`)
|===

The `<ds:KeyInfo>` element must reference the signing `<wsse:BinarySecurityToken>` by its `wsu:Id`. The policy rejects other `KeyInfo` forms, `X509PKIPathv1` and `PKCS7` tokens, external references, and attachment signature transforms.

==== Certificate Requirements

The signing certificate must meet these requirements:

* It's a base64-encoded DER X.509 v3 certificate of up to 16 KiB, with an RSA key of 2048 to 4096 bits.
* It chains to a configured trust anchor through at most eight issuer certificates. The request can include intermediate CA certificates as additional `<wsse:BinarySecurityToken>` elements in the same Security header.
* Every certificate in the chain is valid at the time of the request, and every issuer is a CA certificate.

The policy doesn't check certificate revocation or key usage.

=== Principal Propagation

When UsernameToken validation is enabled and every enabled check succeeds, the policy publishes the matched contract identity so that policies later in the chain can use it:

* `principal` and `client_id`: The client ID of the matched contract.
* `client_name`: The name of the client application.
* `sla-tier-id` and `sla-tier-name` properties: The SLA tier of the contract, when the contract has one.

The policy doesn't publish the client secret or any certificate or signature data. Rejected requests don't change the authentication data.

When only XML Signature validation is enabled, the policy doesn't publish an identity.

=== Security Considerations

Consider these limitations when you configure the policy:

* *No certificate-to-client binding*: When both controls are enabled, a valid signature proves that a trusted signer protected the UsernameToken. It doesn't bind the certificate to the client. Any certificate that chains to a configured trust anchor can sign a UsernameToken for any client ID, which the policy then authenticates separately against API contracts.
* *No replay protection*: The policy requires a signed Timestamp but doesn't enforce its `<wsu:Expires>` value, and doesn't track previously seen requests. Use TLS to protect requests in transit. For more information, see xref:policies-included-tls.adoc[].
* *Multipart attachments aren't inspected*: For `multipart/related` requests, the policy validates only the SOAP envelope in the root part. The root part must use `7bit`, `8bit`, or `binary` `Content-Transfer-Encoding`, or omit the header.
* *XML hardening*: The policy rejects envelopes that contain a `<!DOCTYPE>` declaration or that nest elements more than 128 levels deep.

=== Limits

The policy enforces these fixed limits:

[%header%autowidth.spread,cols="a,a"]
|===
| Item | Limit

| XML element nesting depth
| 128

| `<wsse:BinarySecurityToken>` elements in the Security header
| 16

| Certificates in `trustAnchors`
| 16

| Size of each decoded certificate
| 16 KiB

| Issuer certificates in a certificate chain
| 8

| `<ds:Reference>` elements in a signature
| 16
|===

The request body is also bounded by the Envoy request body limit.

== Request Example

This SOAP 1.1 request carries a signing certificate, a signed Timestamp, a UsernameToken, and a signature that covers both the Timestamp and the UsernameToken:

[source,xml]
----
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/"
               xmlns:wsse="http://docs.oasis-open.org/wss/2004/01/oasis-200401-wss-wssecurity-secext-1.0.xsd"
               xmlns:wsu="http://docs.oasis-open.org/wss/2004/01/oasis-200401-wss-wssecurity-utility-1.0.xsd"
               xmlns:ds="http://www.w3.org/2000/09/xmldsig#">
  <soap:Header>
    <wsse:Security>
      <wsse:BinarySecurityToken wsu:Id="X509-signing-cert"
          ValueType="...#X509v3" EncodingType="...#Base64Binary">MIIB...leaf-cert...</wsse:BinarySecurityToken>
      <wsu:Timestamp wsu:Id="TS-1">
        <wsu:Created>2026-09-30T12:00:00Z</wsu:Created>
        <wsu:Expires>2026-09-30T12:05:00Z</wsu:Expires>
      </wsu:Timestamp>
      <wsse:UsernameToken wsu:Id="UT-1">
        <wsse:Username>contract-client-id</wsse:Username>
        <wsse:Password Type="...#PasswordText">contract-client-secret</wsse:Password>
      </wsse:UsernameToken>
      <ds:Signature><!-- RSA-SHA256 signature that references #TS-1 and #UT-1 --></ds:Signature>
    </wsse:Security>
  </soap:Header>
  <soap:Body><!-- application payload --></soap:Body>
</soap:Envelope>
----

With both controls enabled, Omni Gateway forwards this request when the certificate chains to a configured trust anchor, the signature verifies over `TS-1` and `UT-1`, and the UsernameToken matches an API contract.

== SOAP Faults

When the policy rejects a request, Omni Gateway returns a SOAP fault that matches the SOAP version of the request:

* SOAP 1.1: HTTP status `500` with content type `text/xml`. The Web Services Security fault code is in the `<faultcode>` element.
* SOAP 1.2: HTTP status `400` with content type `application/soap+xml`. The fault code is `env:Sender`, and the Web Services Security fault code is in the `<env:Subcode>` element.

If Omni Gateway rejects the request before it identifies the SOAP version, it returns a SOAP 1.1 fault. Fault messages never include request content or credentials.

[%header%autowidth.spread,cols="a,a,a"]
|===
| Fault Code | Fault String | Condition

| `wsse:InvalidSecurity`
| An error was discovered processing the <wsse:Security> header
| The content type isn't a SOAP media type, the multipart body or SOAP envelope is malformed, or the Security header is missing or duplicated.

| `wsse:InvalidSecurityToken`
| An invalid security token was provided
| The UsernameToken or signing token is malformed.

| `wsse:UnsupportedSecurityToken`
| An unsupported token was provided
| The UsernameToken uses `PasswordDigest`, or the signing token uses an unsupported form.

| `wsse:UnsupportedAlgorithm`
| An unsupported signature or encryption algorithm was used
| The signature uses an unsupported signature, digest, canonicalization, or transform algorithm.

| `wsse:SecurityTokenUnavailable`
| Referenced security token could not be retrieved
| The signing token that `KeyInfo` references can't be found.

| `wsse:FailedCheck`
| The signature or decryption was invalid
| The certificate chain is untrusted, expired, invalid, or incomplete. The signature or a reference digest doesn't verify. The Timestamp or UsernameToken isn't signed when required. The Security header contains XML Encryption.

| `wsse:FailedAuthentication`
| The security token could not be authenticated or authorized
| The client ID doesn't match an API contract, or the client secret is incorrect.
|===

When UsernameToken validation is enabled but API contracts aren't available, Omni Gateway returns a server fault with HTTP status `500` and the fault string `The security token could not be validated at this time`. The fault code is `soap:Server` for SOAP 1.1 and `env:Receiver` for SOAP 1.2, with no Web Services Security subcode.

=== Troubleshoot Rejected Requests

To prevent callers from probing for the cause of a rejection, a single fault code covers several conditions. To identify the exact cause, set the Omni Gateway log level to `debug`. For each rejected request, the policy logs a detailed reason, such as `client ID has no matching API contract` or `certificate chain is not trusted`. Log messages never include credential values. Each rejection also generates a policy violation.
