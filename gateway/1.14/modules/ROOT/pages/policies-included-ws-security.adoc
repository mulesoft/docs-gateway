== Summary

The WS-Security policy validates inbound SOAP 1.1 and SOAP 1.2 requests. You can independently enable UsernameToken authentication against Anypoint API contracts, XML Signature verification against trusted X.509 certificates, or both. When both are enabled, the policy requires a trusted signature over the authenticated UsernameToken.

The policy accepts plain and `multipart/related` SOAP requests and is fail-closed: every enabled control must succeed before the request reaches the backend.

== How This Policy Works

The policy applies the following checks in order. The first failed check determines the fault returned to the client:

. Confirms the request uses an accepted content type (`text/xml`, `application/soap+xml`, or `multipart/related`) and, for multipart requests, that the root SOAP part is well-formed.
. Confirms the selected SOAP envelope is a single, well-formed SOAP 1.1 or SOAP 1.2 document.
. Confirms the envelope contains exactly one direct `<wsse:Security>` header.
. Confirms the elements required by each enabled control are present exactly once, and rejects any direct XML Encryption elements.
. When *Validate XML Signature* is enabled, confirms the signature uses Exclusive XML Canonicalization, RSA-SHA256, and SHA-256 reference digests, with `KeyInfo` referencing a same-header X.509 `BinarySecurityToken`.
. When *Validate XML Signature* is enabled, confirms the signing certificate chains, through at most eight issuer links, to a configured trust anchor.
. When *Validate XML Signature* is enabled, verifies the signature and every reference digest. The covered references must include the Timestamp and, when *Validate UsernameToken* is also enabled, the UsernameToken.
. When *Validate UsernameToken* is enabled, authenticates the token's username and PasswordText password as an API-contract client ID and client secret.

=== Supported Algorithms and Credentials

The policy supports a fixed, non-configurable set of algorithms for XML Signature verification:

* **Signature algorithm**: RSA-SHA256 (`http://www.w3.org/2001/04/xmldsig-more#rsa-sha256`)
* **Canonicalization**: no-comments Exclusive XML Canonicalization (`http://www.w3.org/2001/10/xml-exc-c14n#`)
* **Reference digest**: SHA-256 (`http://www.w3.org/2001/04/xmlenc#sha256`)

A signature using any other algorithm is rejected.

For UsernameToken authentication, the policy only supports `PasswordText` credentials. It always rejects `PasswordDigest`.

=== Principal Propagation

When *Validate UsernameToken* is enabled, after every enabled check succeeds the policy sets `principal` and `client_id` to the matched API-contract client ID, `client_name` to the contract's client name, and, when the contract has an SLA tier, `sla-tier-id` and `sla-tier-name`. No client secret, certificate material, or signature bytes are published.

Signature-only mode doesn't publish an authentication identity. When both controls are enabled, a valid signature proves that a trusted signer protected the token, not a certificate-to-contract identity binding: any certificate chaining to a configured trust anchor can sign for any UsernameToken username, subject to the separate contract-authentication check.

== Examples

=== Accepted Request Shape

The following SOAP request carries a `BinarySecurityToken`, a signed `Timestamp`, a `UsernameToken`, and a signature covering both:

[source,xml]
----
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/"
               xmlns:wsse="http://docs.oasis-open.org/wss/2004/01/oasis-200401-wss-wssecurity-secext-1.0.xsd"
               xmlns:wsu="http://docs.oasis-open.org/wss/2004/01/oasis-200401-wss-wssecurity-utility-1.0.xsd"
               xmlns:ds="http://www.w3.org/2000/09/xmldsig#">
  <soap:Header>
    <wsse:Security>
      <wsse:BinarySecurityToken wsu:Id="X509-signing-cert"
          ValueType="...#X509v3" EncodingType="...#Base64Binary">MIIB...leaf-cert...</wsse:BinarySecurityToken>
      <wsu:Timestamp wsu:Id="TS-1">
        <wsu:Created>2026-09-30T12:00:00Z</wsu:Created>
        <wsu:Expires>2026-09-30T12:05:00Z</wsu:Expires>
      </wsu:Timestamp>
      <wsse:UsernameToken wsu:Id="UT-1">
        <wsse:Username>contract-client-id</wsse:Username>
        <wsse:Password Type="...#PasswordText">contract-client-secret</wsse:Password>
      </wsse:UsernameToken>
      <ds:Signature><!-- RSA-SHA256 references #TS-1 and #UT-1 --></ds:Signature>
    </wsse:Security>
  </soap:Header>
  <soap:Body><!-- application payload --></soap:Body>
</soap:Envelope>
----

When *Validate UsernameToken* and *Validate XML Signature* are both enabled, and the certificate chains to a configured trust anchor, the signature verifies over both `TS-1` and `UT-1`, and the UsernameToken matches an API contract, the original request reaches the backend and the contract identity is available to downstream policies.

=== UsernameToken-Only

With *Validate UsernameToken* enabled and *Validate XML Signature* disabled, the policy authenticates the PasswordText UsernameToken against API contracts and publishes the matched identity. It doesn't require, inspect, or trust an XML Signature.

=== Signature-Only

With *Validate XML Signature* enabled and *Validate UsernameToken* disabled, the policy requires a trusted signature covering the Timestamp. It doesn't require or authenticate a UsernameToken, and it doesn't publish an authentication identity.
