== Summary

The Request Signature Verification policy confirms that an inbound HTTP request originated from a trusted sender. The policy recomputes an HMAC-SHA256 signature over the request's raw body and compares it against the signature the request carries in a header. If the signatures match, the request is forwarded to the upstream unchanged. If verification fails for any reason, the policy rejects the request with a `401 Unauthorized` and the backend is never reached.

Use this policy to protect webhook receivers, such as Slack events, GitHub webhooks, or Stripe webhooks, without adding verification code to the backend service.

Different senders might sign requests in different ways, for example, which header carries the signature, how the signed string is assembled, whether a timestamp bounds replay, and what prefix the signature uses. The policy captures those differences in a `profile` configuration that selects a built-in preset.

A successful verification establishes request _provenance_—it proves the request was signed by the holder of the sender's shared secret. 

This policy only proves a request was sent by a holder of the sender's shared secret. The policy doesn't establish a per-user identity, so the policy does not publish an authenticated principal object for DataWeave parameters.

[NOTE]
====
The signature is computed over the exact bytes the sender signed, so you must place the policy *before* any policy that modifies the request body. For more information, see <<placement>>.
====

The `profile` value selects a built-in preset that fixes every scheme parameter for that sender.

| `{timestamp}.{raw_body}`

| Yes

== How This Policy Works

The policy runs as an inbound request filter. For each request, it buffers the headers and body, resolves the profile's parameters, and runs the verification checks below. The policy only reads the request, and never modifies the body or headers.

The verification checks run in this order. For profiles that carry no timestamp (such as `github`), the timestamp checks are skipped:

. *Signature header present.* Reads the profile's signature header. If it's absent, empty, or unparseable (for a composite header such as Stripe's), verification fails.
. *Timestamp present and well-formed* (timestamped profiles only). Reads the profile's timestamp and parses it as a Unix epoch-seconds integer. If it is absent, empty, or non-numeric, verification fails.
. *Timestamp within tolerance* (timestamped profiles only). If the absolute difference between the current time and the request timestamp exceeds `timestampToleranceSeconds`, verification fails. Both past and future directions are bounded, so a far-future timestamp is also rejected. This check runs before the signature is recomputed.
. *Recompute the signature.* Build the profile's basestring from the request's timestamp value and the raw buffered body, compute `HMAC-SHA256(signingSecret, basestring)`, and encode it as lowercase hex with the profile's prefix.
. *Constant-time compare.* Compare the recomputed signature against the supplied signature using a constant-time byte comparison. If the signatures aren't the same, verification fails. Otherwise, the request is forwarded upstream unchanged.

[[placement]]
== Placement

Because the signature is verified against the exact bytes the sender signed, apply this policy *before* any policy that transforms the request body. If an earlier policy rewrites the body before this policy runs, the recomputed signature will not match and legitimate requests are rejected.

=== Raw Body Handling

The HMAC is computed over the raw buffered body bytes—never a parsed and re-serialized form. The policy doesn't parse the body as JSON or form data and doesn't depend on `Content-Type`. The buffered body is bounded by Envoy's platform-default request-body limit.

== Request and Response Examples

A request with a matching signature—and, for timestamped profiles, a timestamp inside the tolerance window—is forwarded upstream unchanged. For the `github` profile, which carries no timestamp, `timestampToleranceSeconds` is ignored.

Any verification failure returns the following response, and the request never reaches the backend:

----
HTTP/1.1 401 Unauthorized
Content-Type: application/json

{"error":"unauthorized","message":"Invalid request signature"}
----

The body is identical for every failure reason.

The specific failure reason for the failure is only emitted in policy violation logs. The signing secret, the recomputed signature, and the supplied signature are never logged. These are the specific failure reasons:

[%header%autowidth.spread]
|===
| Reason | Meaning

| `missing_signature` | The profile's signature header is absent or empty.
| `malformed_signature` | A composite signature header is present but cannot be parsed.
| `missing_timestamp` | The profile's timestamp is absent or empty (timestamped profiles).
| `malformed_timestamp` | The timestamp is present but is not a base-10 integer.
| `stale_timestamp` | The timestamp is outside the tolerance window (replay defense).
| `signature_mismatch` | The recomputed signature does not equal the supplied signature.
|===
