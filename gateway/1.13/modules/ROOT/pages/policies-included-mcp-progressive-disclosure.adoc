== Summary

The MCP Tools Progressive Disclosure policy reduces an MCP client's context-window token cost by hiding the `tools/list` catalog behind these tools:

* *`search_tools`*: Finds relevant tools on demand by matching a query against tool names and descriptions
* *`invoke_tool`*: Calls a tool discovered via `search_tools`

With this policy, you can:

* Reduce token consumption by exposing tools on-demand rather than listing all tools up front
* Keep frequently-used tools immediately available through `hotTools` configuration
* Maintain per-caller authorization by delegating access control to the policy chain
* Support paginated search results for large tool catalogs
* Preserve normal tool invocation semantics for upstream policies

The policy holds *no resident catalog and performs no caching*. Every `tools/list`, `search_tools`, and `invoke_tool` request is resolved against a live upstream round-trip, so the client always sees the real, per-caller-filtered upstream state.

== Configuring Policy Parameters

include::partial$policy-title-headers.adoc[tag=configFileTitleOnly]

The MCP Tools Progressive Disclosure policy isn't supported in Local Mode.

include::partial$policy-title-headers.adoc[tag=ui]

[%header%autowidth.spread,cols="a,a,a"]
|===
| Element | Description | Default
| Search Result Limit | The maximum number of matches a `search_tools` query returns per page when the query omits its own `limit` parameter. | `20`
| Hot Tools | Tool names or glob patterns that bypass disclosure. Matched tools appear in the client-facing `tools/list` alongside the two meta-tools, carrying their original upstream schemas. | `[]` (empty)
| Meta Tool Prefix | A prefix prepended to the `search_tools` and `invoke_tool` meta-tool names to avoid namespace collisions with upstream tool names. | `""` (empty)
|===

=== Configuration Example

[source,yaml]
----
- policyRef:
    name: mcp-tools-progressive-disclosure-policy-flex
  config:
    searchResultLimit: 20
    hotTools:
      - "get_weather"
      - "list_*"
    metaToolPrefix: ""
----

== How It Works

=== Meta-Tool Advertisement

When a client requests `tools/list`, the policy:

. Forwards the request upstream to get the live, per-caller-filtered tool catalog
. Replaces the full catalog with the two meta-tools (`search_tools` and `invoke_tool`)
. Includes any tools matching the configured `hotTools` patterns with their original schemas

=== Tool Discovery

When a client calls `search_tools`:

. The policy forwards a synthesized `tools/list` request upstream
. The upstream access control policy filters the list per caller
. The policy runs the search query against the filtered list
. Matching tools are returned with their full schemas, sufficient to construct an `invoke_tool` call

=== Tool Invocation

When a client calls `invoke_tool`:

. The policy rewrites the request as a native `tools/call` with the wrapped tool name
. All upstream policies see the real tool name (not `invoke_tool`)
. The response is returned to the caller unchanged

This normalization ensures that access control, tool mapping, and other policies operate on the real tool name without progressive-disclosure awareness.

== Hot Tools Configuration

The `hotTools` configuration enables you to keep frequently-used tools immediately visible without requiring a search. Tools matching the patterns appear in `tools/list` alongside the two meta-tools.

=== Pattern Matching

* Use exact names: `"get_weather"`
* Use glob patterns: `"list_*"`, `"*_info"`
* Matches are evaluated against the live upstream `tools/list` response on every request
* Only tools the caller is authorized to see (per the chain's access control policy) will match

=== Use Cases

*Frequently-used tools*: Keep high-traffic tools immediately available to reduce search round-trips.

[source,yaml]
----
hotTools:
  - "get_weather"
  - "get_user"
----

*Namespace patterns*: Expose all tools from a specific namespace.

[source,yaml]
----
hotTools:
  - "weather_*"
  - "user_*"
----

== Search Tool Usage

The `search_tools` meta-tool accepts a JSON object with the following parameters:

[%header%autowidth.spread,cols="a,a,a,a"]
|===
| Parameter | Type | Required | Description
| `query` | string | Yes | A case-insensitive regular expression to match against tool names and descriptions. Separate alternative keywords with `\|` (spaces match literally).
| `limit` | integer | No | Maximum number of results to return per page. If omitted, uses the configured `searchResultLimit`.
| `cursor` | string | No | Opaque pagination cursor from a prior search's `nextCursor` field. Pass it back to fetch the next page.
|===

=== Example Request

[source,json]
----
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "search_tools",
    "arguments": {
      "query": "weather",
      "limit": 3
    }
  }
}
----

=== Example Response

[source,json]
----
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "Found 1 matching tool(s)."
      }
    ],
    "structuredContent": {
      "matches": [
        {
          "name": "get_weather",
          "description": "Return the current weather for a city",
          "inputSchema": {
            "type": "object",
            "required": ["city"],
            "properties": {
              "city": {
                "type": "string"
              }
            }
          }
        }
      ]
    }
  }
}
----

=== Pagination

When more tools match than fit on a page, the response includes a `nextCursor` field under `structuredContent`:

[source,json]
----
{
  "structuredContent": {
    "matches": [...],
    "nextCursor": "eyJxIjoid2VhdGhlciIsIm8iOjIwfQ=="
  }
}
----

To fetch the next page, pass the cursor back in the `arguments`:

[source,json]
----
{
  "method": "tools/call",
  "params": {
    "name": "search_tools",
    "arguments": {
      "cursor": "eyJxIjoid2VhdGhlciIsIm8iOjIwfQ=="
    }
  }
}
----

Each page resolves against a fresh upstream `tools/list`, ensuring current authorization state. The `query` parameter may be omitted when using a cursor (the cursor carries it).

== Invoke Tool Usage

The `invoke_tool` meta-tool wraps a call to a discovered tool. It accepts:

[%header%autowidth.spread,cols="a,a,a,a"]
|===
| Parameter | Type | Required | Description
| `name` | string | Yes | The tool name returned from `search_tools`
| `arguments` | object | Yes | The tool's input parameters as returned in the `inputSchema` from `search_tools`
|===

=== Example Request

[source,json]
----
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "invoke_tool",
    "arguments": {
      "name": "get_weather",
      "arguments": {
        "city": "San Francisco"
      }
    }
  }
}
----

The policy rewrites this as a native `tools/call`:

[source,json]
----
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": {
      "city": "San Francisco"
    }
  }
}
----

All upstream policies see `get_weather` (not `invoke_tool`), ensuring access control, tool mapping, and other policies operate correctly.

== Filter Chain Ordering

The MCP Tools Progressive Disclosure policy *must be positioned first* in the MCP filter chain, before any policy that reads tool names (access control, tool mapping, schema validation).

If positioned after an access control policy, that policy would see `invoke_tool` (the meta-tool) in the request and gate the envelope—not the real tool inside—creating an authorization bypass.

At configuration load, the policy emits:

* A WARN-level log message
* The metric counter `mulesoft_mcp_tools_progressive_disclosure_ordering_signal`

These signals remind operators that correct ordering is required. The policy cannot detect or enforce its position at runtime.

=== Recommended Chain Order

[source,yaml]
----
policies:
  - policyRef:
      name: mcp-tools-progressive-disclosure-policy-flex  # FIRST
  - policyRef:
      name: mcp-attribute-access-control-policy-flex
  - policyRef:
      name: mcp-tool-mapping-policy-flex
  - policyRef:
      name: mcp-support-policy-flex                       # LAST
----

== Delegated Authorization

The policy maintains per-caller authorization parity by delegating to the chain:

. A `search_tools` call triggers a synthesized `tools/list` request upstream
. The upstream access control policy filters the list per caller
. The policy runs the query against the filtered list
. Only tools the caller is authorized to see are included in results

This delegation ensures:

* No caller sees tools they cannot invoke
* Results reflect live authorization state
* No caching of authorization decisions

If no access control policy is present, `search_tools` returns the full unfiltered catalog—the same as a direct `tools/list` would in that chain.

== Error Responses

The policy returns JSON-RPC error objects with a stable `data.reason` field for machine-checkable error handling.

[%header%autowidth.spread,cols="a,a,a,a"]
|===
| Case | Code | `data.reason` | Description
| Malformed `invoke_tool` | `-32602` | `invalid_params` | Missing or invalid `arguments.name` or `arguments.arguments`
| Malformed `search_tools` | `-32602` | `invalid_params` | Empty/missing/non-string query, exceeds 256 characters, invalid regex, bad `limit`, missing `id`, malformed `cursor`, or `cursor`/`query` mismatch
|===

The policy originates only `invalid_params` errors. It holds no catalog, so it never rejects an `invoke_tool` call as `unknown_tool`—an unknown wrapped tool is normalized, forwarded, and surfaces as the upstream error.

Errors produced upstream (access control denials, upstream tool errors) pass through unchanged.

== Token Savings

The policy reduces token consumption by replacing large `tools/list` catalogs with two concise meta-tool schemas.

=== Before (Full Catalog)

A `tools/list` with 50 tools, each with a 200-token schema = ~10,000 tokens per list.

=== After (Progressive Disclosure)

* Two meta-tool schemas = ~400 tokens
* `hotTools` (optional) = variable, typically < 1,000 tokens for a few tools
* `search_tools` query + results = ~200–2,000 tokens depending on result count

For a workflow with multiple `tools/list` calls, savings compound significantly.

=== Token Metrics

The policy tracks before/after token counts in the `_mcp_token_metrics` field on responses:

* `pre_transform`: Estimated tokens in the upstream catalog (before optimization)
* `response`: Estimated tokens in the rewritten response (after optimization)

The downstream `mcp-support-policy` extracts these metrics and emits them as:

* `mulesoft.mcp.pre_transform_tokens`
* `mulesoft.mcp.response_tokens`

These metrics are advisory estimates (~4 bytes per token heuristic) and do not influence routing or filtering behavior.
